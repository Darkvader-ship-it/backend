# Error reference

Every error from the API uses one JSON shape. This page lists each status and
message the backend can return, where it is raised in the source, and what a
client should do.

## Response shape

```json
{ "success": false, "error": "Validation failed", "details": [{ "field": "sku", "message": "\"sku\" is required" }] }
```

- `success` is always `false`.
- `error` is a human-readable message. It can include values (IDs, SKUs, counts),
  so do not match on its exact text beyond the table below.
- `details` appears only on 400 validation errors and on errors raised with details.
  Each item has `field` (dot path into the body) and `message`.
- `stack` is added to 5xx responses outside production only.

There is no separate numeric error code in the response body. The HTTP status
is the only numeric code. Key your handling on the status first, then on the
message for the cases listed below.

Rate limits (429) set `RateLimit` and `RateLimit-Policy` headers (draft-7).

## How clients should handle each class

- **400 (validation and business rules).** The request is wrong. Show `details`
  next to the fields, or show `error`. Do not retry the same body. Business-rule
  400s (amount, discount, cash) need a corrected value from the user.
- **401 (authentication).** Clear the stored token and send the user to sign in
  when the message is `Authentication required`, `Invalid or expired token` or
  `Account no longer exists`. For login and 2FA messages, let the user retry.
  Do not auto-retry login. Login and 2FA prompts are generic on purpose.
- **402 (Stellar payment not verified).** Payment did not match on-chain. Keep the
  sale open. Show the reason from the message and ask for a new payment.
- **403 (role).** Do not retry. Hide or disable the action for that role.
- **404 (not found).** Refresh the list or detail view. The record may be gone.
  For `Route not found`, check the path and `/api/v1` prefix.
- **409 (conflict).** The state changed or the value is taken. Reload the
  resource, then decide. For stock, reduce the quantity. For duplicate SKU or
  email, pick another value. For sale status and reused Stellar hashes, do not
  resend the action.
- **429 (rate limit).** Back off until the window resets. Respect the `RateLimit`
  headers. For login, wait 15 minutes.
- **500 (server error).** Retry reads with backoff. For writes, read the record
  first, because the write may have happened. Report the time and route.
- **503 (Stellar not configured).** Hide the Stellar payment option. Other 503s
  on `/health` mean the load balancer should send traffic elsewhere.

## Known quirks

- A request body above the 100 KB `express.json()` limit (`src/app.ts:47`) is
  not a SyntaxError, so `src/middleware/error.middleware.ts:23` does not treat it
  as 400. By code reading, it becomes a 500 (`Internal server error` in
  production). This was not tested.
- `verifyToken` throws `Invalid token` (`src/middleware/auth.middleware.ts:31`).
  `authenticate` catches it and returns `Invalid or expired token`, so clients
  should expect the latter.
- `sendError` (`src/utils/helpers.ts:17`) builds the same envelope without
  `details`. No route calls it, so the errors above are all from `AppError`.
- Some `Error`s (for example `src/utils/money.ts:12`) are not `AppError`. They
  become a 500 unless a route converts them.

## Where errors are produced

- `AppError(message, statusCode, isOperational, details)` in
  `src/middleware/error.middleware.ts:5`. Helpers `badRequest` (`:17`),
  `notFound` (`:18`) and `conflict` (`:19`) wrap it.
- `notFoundHandler` (`src/middleware/notFound.middleware.ts:4`) for unknown routes.
- `errorHandler` (`src/middleware/error.middleware.ts:21`) is the last middleware
  and writes the envelope (`:41-46`).
- `authenticate` and `authorize` (`src/middleware/auth.middleware.ts:36-58`).
- `validateBody` (`src/middleware/validate.middleware.ts:11-32`).
- `roleRateLimit` (`src/middleware/rateLimit.middleware.ts:32`) and the auth
  limiter (`src/routes/auth.routes.ts:21-27`) return their own envelope.
